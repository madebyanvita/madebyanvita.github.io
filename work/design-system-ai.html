Case study 05 · Tim Hortons · Exploration, not shipped

Teaching the design system to speak code.

Design and product would agree on a direction; engineering would build something slightly different. There was no shared, structured source that both sides worked from. I explored closing that gap with AI tools. In Cursor, I rebuilt the Tim Hortons colour system as 45 Material 3 roles that generate Figma variables for light and dark mode, and tested them against real flows. I also designed a guided intake that turns a screen request into a reviewable wireframe. It paused before production, so this is about the thinking and the craft, not a launch.

Act I

The mess.

Agreed in the room, different in the build

Design, product and engineering were aligned on paper but worked in parallel tracks. Product and design would settle on a direction, then engineering would build it independently, and the result often drifted from what had been agreed.

  1. Requests arrived in pieces. Intent was scattered across Slack threads and tickets, so every screen started with reassembling what was actually being asked.
  2. Mocks came before structure. High-fidelity Figma screens were built before anyone had agreed how the screen should work, which hid structural mistakes under polish.
  3. The same debates, every sprint. "Modal or push?", which navigation title, which controls: settled again each time, with copy invented on the spot.

A new app initiative, and the design-system refresh that came with it, was the chance to fix this at the root rather than paper over it with more meetings.

The real questionCould design and engineering build from the same structured source, one that people and AI tools could both read?

Act II

The meaning.

Three goals

  1. Move faster, together. Close the gap between what design and product agree on and what engineering ships.
  2. One consistent foundation. Tokens that work the same in light and dark mode, so theming is a variable swap, not a redesign.
  3. Build for AI, not just people. Rules clear enough that designers and AI agents like Cursor and the Figma MCP can build from them directly.

How a brief moves through the system

The model was simple: a brief, a prompt or a rough sketch becomes a blueprint, a structured description of the screen. Copy, assessments, a prototype or code, and the Figma design are all generated from that one blueprint, and every output is built on the same tokens, patterns and rules.

Act III

The work.

A colour system named for the job, not the shade

Rather than invent a token system from scratch, I built on Material Design 3's architecture: roles like surface, on surface and primary container, instead of names tied to a specific colour. One role name works in both modes; the theme decides the value, so nobody re-derives it screen by screen.

In Cursor, I wrote this down as a structured 45-role colour system and generated Figma variables directly from it, with light and dark mode bound to the same role names. In dark mode, Tim Hortons primary becomes yellow, not red, and every screen follows without being redrawn.

Where the automation got it wrong

AI-generated tokens still need a designer's eye. Testing the system against real screens surfaced gaps the automation missed, and the clearest was the toggle switch: the first pass didn't treat the off-state track correctly, so the switch almost disappeared on dark surfaces.

I went back to Material 3's own switch anatomy, then tested seven stroke candidates against the same track, checking contrast and whether each one stayed on-palette. The working pair was surface container highest as the track fill and outline as the stroke, at 5.6:1 against the track, in both light and dark mode.

Generated isn't the same as designed.

Rules for structure, not just colour

Tokens define what a colour does. A second layer of rules defines how content and controls are arranged. With another designer, I wrote a first pass of layout and component guidance, and with a copywriter, content rules for consistent microcopy.

  • LayoutSurface hierarchy, sections, page padding and margins, grids and scroll behaviour.
  • Fields and controlsText, link, action, input, checkbox, radio, toggle, stepper and segmented control.
  • Feedback and loadingWhen to use alerts, modals or sheets; skeletons versus spinners; busy states and lost connectivity.
  • App patternsPage headers, sticky footers, keyboards, navigation stacks, back behaviour and form validation.

These rules were written but not yet tested against real screens. That would have been the next validation pass, using the same method that caught the toggle: apply the rule, build a real screen with it, fix what doesn't hold up.

A front door for screen requests

The tokens decide what a screen looks like. The intake decides how a request is structured before anyone opens Figma. I designed it as a guided wizard backed by a single catalogue of journeys and screens.

Instead of a designer, or an AI agent, guessing at modal versus push, the navigation title or which controls apply, the system infers them from the catalogue after a few branching questions: is this an existing flow or a new one, what should the guest get done, and where does it live in the app?

The output defaults to a wireframe first. High fidelity and code or Figma generation are later, opt-in steps, because polish that arrives too early hides the wrong structural decisions.

The same intake runs in Cursor chat and in a browser preview, so one set of logic serves both AI-agent work and manual design work.

From blueprint to screen

To see whether the pieces held together, I built an HTML prototype with screen-building and test-screen views. Each example blueprint renders in a fixed iPhone-sized frame next to its spec, with every region of the screen mapped to its blueprint control, its code component and its catalogue entry, and previewable in its default, error and submitting states.

Learnings

What I'm taking with me.

  1. Design-systems work starts before the components. Designing how a request enters the system mattered as much as the tokens it ends up using.
  2. AI needs constraints to be useful. A catalogue and inferred rules gave the tools something to reason with. Open-ended prompts gave them room to guess.
  3. Test in context, not on a grid. The toggle looked fine as a swatch. It only failed on a real screen, and a designer's eye is what caught it.

Where it stands

Paused, not finished.

The work paused before it went into production. The system lived in its own design repo, separate from engineering's codebase. The next steps would have been:

  • One source of truthMerge the design and engineering repos, so both sides build from the same files, not parallel copies.
  • Test the rulesRun the layout and component rules against real screens, the way the colour system was tested.
  • More golden pathsExpand the scenarios that generated screens are checked against.
  • A prompt in the roomProduct, design and engineering react to a rough generated screen together, instead of waiting days for a first mock.

The intake turns a brief into structure. The tokens turn structure into something that looks and feels like Tim Hortons.

Case study 05 · Tim Hortons · Design system + AI

I taught our design system to build with us.

Design and product would agree on a direction, and engineering would build something slightly different, because our decisions lived in people's heads, not anywhere a person or a tool could read. With another designer, I wrote those decisions down as a skill: a Markdown file of rules that AI tools load in our prototyping sandbox. I owned the colour system underneath it, and the intake that turns a request into a prototype. Our team now uses it to design and to build front end. A prototype that took two or three days now takes about half a day. It isn't perfect, and we're still refining it.

Act I

The mess.

Agreed in the room, different in the build

Design, product and engineering were aligned on paper but worked in parallel tracks. Product and design would settle on a direction, then engineering would build it independently, and the result often drifted from what had been agreed.

  1. Requests arrived in pieces. Intent was scattered across Slack threads and tickets, so every screen started with reassembling what was actually being asked.
  2. Mocks came before structure. High-fidelity Figma screens were built before anyone had agreed how the screen should work, which hid structural mistakes under polish.
  3. The same debates, every sprint. "Modal or push?", which navigation title, which controls: settled again each time, with copy invented on the spot.

AI tools could already generate screens quickly. But they didn't know any of our decisions: not our colours, not how our error states work, not which component to use where. Fast output that ignores the system just creates more cleanup.

Speed brought a second problem. When anyone can make a credible-looking screen in minutes, it's tempting for everyone to go off and build ideas alone. There's nothing wrong with brainstorming, but it wastes time when people end up doing each other's jobs, and work can slip through without the right experts ever seeing it. We wanted to decide together, not in isolation.

The tools will always produce a design. The question is whether it's the right one.

A new app initiative, and the design-system refresh that came with it, was the chance to fix this at the root rather than paper over it with more meetings.

The real questionWhat if everything we already knew about designing this app was written down once, in a form both people and AI tools could build from?

Act II

The meaning.

Three goals

  1. Move faster, together. Close the gap between what design and product agree on and what engineering ships.
  2. One consistent foundation. Tokens that work the same in light and dark mode, so theming is a variable swap, not a redesign.
  3. Build for AI, not just people. Rules clear enough that designers and AI agents like Cursor and the Figma MCP can build from them directly.

The idea: write it down once, as a skill

A skill is a Markdown file that an AI tool loads before it starts working. Ours holds the rules we'd learned from designing across channels, in four layers: UX, UI, behaviour and content. That covers how tokens work, how each component behaves, and how error, loading and empty states show up. Load the skill in the sandbox, and the tool builds the way our team would, instead of guessing.

How a request moves through the system

A brief, a prompt or a rough sketch becomes a blueprint, a structured description of the screen. Copy, assessments, a prototype or code, and the Figma design all come from that one blueprint, and every output is built on the same tokens, patterns and rules.

A blueprint is a recipe for a screen

Every blueprint follows the same recipe, so a person or a tool can read it the same way. It starts with the biggest decision, whether this is a page or a modal, then breaks the screen down into sections and cards, and each of those into fields with a title, subtitle and helper.

Act III

The work.

The layer I owned: colour, named for the job, not the shade

Rather than invent a token system from scratch, I built on Material Design 3's architecture: roles like surface, on surface and primary container, instead of names tied to a specific colour. One role name works in both modes; the theme decides the value, so nobody re-derives it screen by screen.

In Cursor, I wrote this down as a structured 45-role colour system and generated Figma variables directly from it, with light and dark mode bound to the same role names. In dark mode, Tim Hortons primary becomes yellow, not red, and every screen follows without being redrawn.

Where the automation got it wrong

AI-generated tokens still need a designer's eye. Testing the system against real screens surfaced gaps the automation missed, and the clearest was the toggle switch: the first pass didn't treat the off-state track correctly, so the switch almost disappeared on dark surfaces.

I went back to Material 3's own switch anatomy, then tested seven stroke candidates against the same track, checking contrast and whether each one stayed on-palette. The working pair was surface container highest as the track fill and outline as the stroke, at 5.6:1 against the track, in both light and dark mode.

Generated isn't the same as designed.

Rules for everything beyond colour

Tokens define what a colour does. The rest of the skill defines how content and controls behave. With another designer, I turned our past design work into layout, component and state rules, and with a copywriter, content rules for consistent microcopy.

Feedback

  • Native alerts, modals or form sheets: when to use each
  • Modern feedback in place of toast messages
  • Confirm on destructive actions, or on dismiss
  • When a message should appear as an error

Loading

  • Skeletons or spinners
  • Busy states on buttons, and the rest of the form while busy
  • Optimistic updates with rollback
  • Low connectivity versus lost connectivity

Navigation

  • Screen or modal
  • Nested modals within a stack
  • How screen flows and modal flows work
  • Back on iOS and Android, including gestures

Layout

  • Surface hierarchy and sections
  • Page padding, margins and grids
  • Scroll behaviour
  • Sticky CTAs and page footers per platform

Fields and controls

  • Text, link, action and input fields
  • Checkbox, radio, toggle, stepper, segmented control
  • Badges, dots and unread counts
  • Validation on blur or on submit, and auto-fill

Platform and access

  • Haptics, shadows and animation
  • Safe areas and permissions
  • Font scaling
  • Alt text

We refine the rules the same way I fixed the toggle: build a real screen with the skill, look at what it got wrong, and tighten the rule that let it happen.

From a few questions to a prototype

When someone asks for a screen, the hardest part is working out what they actually need. I'd always done that with a series of questions, so I turned my own workflow into the skill's front door: a guided intake backed by a catalogue of journeys and screens.

Instead of a designer, or an AI agent, guessing at modal versus push, the navigation title or which controls apply, the skill infers them from the catalogue after a few branching questions.

The answers go to the skill, which builds a first prototype in the sandbox from our real tokens and components. It isn't perfect, but it's close enough to react to, and that's the point: the conversation starts from a screen, not a blank page.

The same intake runs in Cursor chat and in a browser preview, so one set of logic serves both AI-assisted work and manual design work.

Design, shipped like code

The skills live where the code lives: in their own branch of the app's repository. Designers and our copywriter work on their own machines, commit changes, and open a pull request, so every change to a rule gets reviewed before it reaches the main branch, just like a change to the app.

Components the skill can build with

A skill is only as good as the parts it can reach for. Alongside the rules, I built components for our new design system, so the skill assembles real, documented pieces instead of approximations: foundations, fields, pickers, buttons, page chrome and feedback, then patterns and screens on top.

From blueprint to screen

To check the pieces hold together, I built test screens: everyday flows like sign in, sign-in errors, account, joining and customising a coffee, each built from its blueprint with our tokens and components. Each one renders next to its spec, with every region mapped to its blueprint control, code component and catalogue entry, so engineers see exactly what to build.

Learnings

What I'm taking with me.

  1. Design-systems work starts before the components. Designing how a request enters the system mattered as much as the tokens it ends up using.
  2. Write down what designers know. Most of the skill wasn't new thinking. It was decisions from our past design work, finally written down where a tool could use them.
  3. AI needs constraints to be useful. A catalogue and inferred rules gave the tools something to reason with. Open-ended prompts gave them room to guess.
  4. Test in context, not on a grid. The toggle looked fine as a swatch. It only failed on a real screen, and a designer's eye is what caught it.

What's next

In use, still evolving.

The skill still gets things wrong, and every generated screen gets a designer's review. But each mistake now improves a rule, instead of being fixed once and forgotten. What we're focused on next:

  • Test more rulesRun every layout and component rule against real screens, the way the colour system was tested.
  • More golden pathsExpand the scenarios that generated screens are checked against.
  • A prompt in the roomProduct, design and engineering react to a rough generated screen together, instead of waiting days for a first mock.
  • Room for hero momentsThe scan screen, the homepage and rewards are one-offs that deserve bespoke design. The question we're working through: how do we use the same tools to break some rules, but follow others?

The intake turns a request into structure. The skill turns structure into something that looks, works and feels like Tim Hortons.
